| R-01 | 01 | Referral-partner bank `account_number` stored in plaintext in Postgres (`referral_partner_banking`); the code comment implies encryption is available but `STORAGE_ENCRYPTION_KEY` only covers uploaded files, not DB columns, so this field is not actually protected by that mechanism today | P1 | Engineering | Add field-level encryption (application-layer AES-GCM, keyed separately from file storage) | **CLOSED 2026-08-08.** `server/src/lib/fieldCrypto.ts` (new, always-on AES-256-GCM, key derived via HKDF from `SESSION_SECRET` - no new required env var). Wired into all 5 read/write sites in `referral-partner-onboarding.ts` for `account_number`, `routing_number`, and `iban` (the last of which was previously returned to clients fully unmasked - closed as part of the same fix). Verified live: raw DB column now holds base64 ciphertext (`RFBGM...`, the `DPF1` magic header); the owning partner's own `GET` returns correctly masked values (`****6789` etc.) derived by decrypting server-side, never the ciphertext or the full value. 5 new unit tests in `tests/fieldCrypto.test.ts`. Legacy plaintext rows (none existed in this environment) would continue to read correctly unchanged - no backfill migration required to deploy safely. |
